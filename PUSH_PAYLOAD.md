# Текст сообщения и переход в чат

Клиент принимает `chat_id` / `chatId`, необязательный `message_id` / `messageId` и текст `message`. Поддерживается как обычный FCM `data`, так и старый вложенный формат (объект или JSON-строка):

```json
{"data":{"message":"test2","chat_id":"019cb94e-73c1-710f-9208-cfef55ef91e8"}}
```

В открытом приложении баннер показывает `message`, экранируя HTML. Нажатие системного уведомления передаёт его данные в нормализатор и открывает `/dialogs/<chat_id>`. Если нужен вход или PIN, router сохраняет целевой путь в `redirect`. Необходимость ввода PIN не обходится.

## Payload для серверной отправки через FCM HTTP v1

```json
{
  "message": {
    "token": "<FCM_TOKEN_УСТРОЙСТВА>",
    "notification": {
      "title": "Сообщение от Оператор",
      "body": "test2"
    },
    "data": {
      "message": "test2",
      "chat_id": "019cb94e-73c1-710f-9208-cfef55ef91e8"
    },
    "android": {
      "notification": {
        "channel_id": "messages",
        "icon": "ic_stat_finclub"
      }
    }
  }
}
```

Все значения FCM `data` должны быть строками. Auth-токен для входа в FinClub не является FCM-токеном устройства.

Рекомендуемый серверный контракт: **не сериализуйте объект `data` в `notification.body`**. Обычно в фоне или при завершённом процессе Android SDK показывает `notification.body` напрямую, без JavaScript приложения. В стандартном payload сервер отправляет `"body": "test2"`, а `chat_id` — в отдельном `message.data`. Это также не требует Android-специфичной совместимости на iOS.

Разбор JSON в JavaScript сам по себе не меняет уже показанную Android карточку и не восстанавливает отсутствующий в событии `chat_id`. Изменения сервера в этом frontend-репозитории не выполнялись.

## Android: совместимость с JSON в body

Для существующего backend добавлена app-owned `LegacyMessagingService`: до показа карточки она разбирает legacy `gcm.n.body` / `gcm.notification.body`, подставляет `message` в текст, а `chat_id` и необязательный `message_id` переносит в обычные data extras. Дальше карточку и PendingIntent создаёт сам Firebase SDK; обработчик нажатия Capacitor получает идентификатор чата. Обычные уведомления и обновление FCM-токена сохраняются.

В manifest зарегистрирован один обработчик `com.google.firebase.MESSAGING_EVENT` вместо сервиса плагина. Делегирование уведомлений Google Play Services отключено и в manifest, и при запуске, чтобы системный proxy не обходил обработку body. Существующие уже показанные карточки эта правка не меняет — проверять нужно новой отправкой после установки APK.

**Техническое ограничение:** pre-display обработка использует public `handleIntent` hook, помеченный Firebase как `@hide`, в установленном SDK **25.0.1**. Это режим совместимости с текущим backend, а не стабильный публичный контракт Firebase. При обновлении SDK обязательны повторная native-проверка, merged-manifest и тест реального background push. Канонический серверный payload выше предпочтителен и позволяет впоследствии удалить этот adapter. На iOS данный Android adapter не действует.

После PIN новый `query.redirect` из push имеет приоритет над старым `redirectAfterPin`, сохранённым idle-таймером. Старое назначение очищается после успешного ввода PIN.

Нативный плагин уже обрабатывает старт приложения по уведомлению и сохраняет событие до подписки JS. Повторно пересылать launch intent из `MainActivity` не требуется.

Источники: [получение сообщений Android](https://firebase.google.com/docs/cloud-messaging/android/receive-messages), [формат FCM message](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages).

## Проверка 29 октября 2026

148/148 тестов и typecheck прошли; независимый review принят. Тестируется настоящий нормализатор, native callbacks и router guard, включая вложенный JSON со скриншота, HTML escaping, неверный JSON/Unicode, приоритет явных routing-полей и сохранение назначения через Auth/PIN.

На Android-эмуляторе проверены имитации tap intent: обычный запуск с плоским `chat_id` и холодный запуск с JSON-строкой `data`. Оба сохранили `/dialogs/019cb94e-73c1-710f-9208-cfef55ef91e8` в `redirect` экрана PIN. PIN не вводился и не обходился. Это проверка обработки события, а не реальной доставки через FCM. Новая реальная отправка с исправленным серверным payload и текст в фоновой шторке пока не проверены.

### Исправление после реальной проверки шторки — APK 1.0.1

Скриншот реального push подтвердил, что прежняя JS-правка не изменяет SDK-карточку. В Android добавлен adapter выше; backend можно оставить с текущим legacy body. Исправлены также приоритет нового назначения над idle-страницей после PIN и обновление экрана при переходе из одного чата в другой. Поздние ответы, SSE и завершение отправки закрытого чата не должны возвращать старый чат.

206/206 JS-тестов, typecheck и 6 нативных тестов payload прошли. APK 1.0.1 (versionCode 2) собран, подпись проверена, установлен на эмулятор после удаления приложения пользователем. **Реальная проверка пользователем завершена:** после повторного входа, разрешения уведомлений и новой отправки push пользователь подтвердил, что отображение и переход работают нормально. Самостоятельная проверка нажатия ассистентом не выполнялась: пользователь уже проверил результат. Регистрация FCM-токена на сервере отдельно подтверждена HTTP 200. Версия SDK и ограничения adapter описаны также в `src-capacitor/android/LEGACY_FCM.md`.
